# 发布流程的 token 消耗评估与优化方案

日期：2026-10-14。此次只评估仓库发布流程并提供方案，未改变发布门槛、实现发布脚本、执行发布验证或部署。

## 结论与评估口径

优先将重复的验证编排、浏览器检查、打包和资源比较固化为脚本，完整日志落盘，模型只读取摘要与异常。完整验证可以继续执行，程序运行时间与模型读取内容量应分开优化。

仓库没有历史发布各次模型调用的 usage 记录，不能给出真实账单、推理 token 或整次发布总 token。本报告的数字仅估算一次读取的新增可见文本量，不包含系统／工具定义、对话上下文再次输入、图像、隐藏推理和缓存计费差异；也不是账号使用额度百分比。实际节省必须用后续同等范围发布的用量数据核验。

字符粗估采用：中文字符每字 1–2 token，其余字符每 3–5 字符约 1 token。没有安装或运行模型 tokenizer，因此范围较宽，仅用于排序优化优先级。

## 当前发布要求与可复用资产

依据 [发布流程](../docs/release.md)、[协作约束](../AGENTS.md)、[1.2.4 发布报告](v1.2.4-release-2026-10-14.md)及对应源码：

- 发布前：完整测试、独立原始计算对照、重复生成与未知摘要拒绝、语法、文档引用、双语桌面与窄屏浏览器检查。
- 打包：干净独立目录，只含 `index.html`、`_redirects`、`src/`、`vendor/`。
- 发布后：十五个路由保留路径、公开资源逐文件一致、双语版本与普通战斗完成。HTML 注入及 `_redirects` 需分别按入口与路由行为验证。
- 最近 1.2.4 发布当时为 277 项测试、49 个发布文件、47 个公开资源；这些是历史数量，应由下一次实际执行重新统计。
- 本地与生产各七页 × 两语言 × 两视口，共 56 组基础布局检查，另有改动专项。不能把上线前检查当作线上验收。
- `reports/all-pages-update-audit-2026-10-13.mjs` 已包含 260 组战斗预测及新装备比较，再加采集、制造、升级、强化及预报；其战斗部分覆盖 `reports/combat-update-audit-2026-10-13.mjs` 的相应核验。常规发布不需要为了同一范围同时运行两个脚本。
- `scripts/` 当前只有 serve、inspect、extract、combat-update；package scripts 只有 start、extract、test。发布编排、通用浏览器验收、打包及生产核验尚未形成这些目录中的统一入口；历史 JSON 是证据，不能代替检查脚本。

## 优先实施方案

### 1. 固定输出契约，保留完整失败证据

所有检查的完整 stdout／stderr 写入本次独立证据目录。成功只回传检查名、数量、耗时、输入摘要和结果路径；失败回传失败用例／路由／文件、相关错误与日志位置，进程保留非零退出码。

测试日志只返回总结时，可将约 1.2万–1.9万 token 的详细输出样例压缩到目标 200–500 token。该目标是输出预算，不是已测实现结果。不能用 `|| true`、忽略 stderr 或只截取最后几行来掩盖失败；取消／跳过需按发布要求明确处理。

### 2. 建立三个可复用发布阶段

建议后续新增以下入口，当前尚未实现：

- `release:check`：完整测试、唯一完整独立对照、生成一致性与未知摘要拒绝、语法、文档链接、本地路由和浏览器检查。
- `release:package`：按白名单构建干净发布包，生成路径／SHA-256 清单，校验版本与禁止夹带的文件。
- `release:verify`：接收明确部署地址和发布清单，批量检查生产路由、公开资源、双语版本、浏览器矩阵及战斗完成。

先复用已核验审计脚本的内容，逐步把需要长期运行的验证从日期型报告脚本提炼到 scripts；保留历史文件作证据。浏览器自动化依赖需要明确声明和安装，不能假设报告中的临时浏览器环境长期存在。

三阶段均输出结构化机器结果，由这些结果生成简短发布报告。脚本负责固定检查，模型处理发布范围、异常与结果解释。

### 3. 针对同一候选发布只做一轮完整验证

先完成版本号与发布范围变更，再固定候选输入，运行完整检查。全部通过后打包、核对摘要、部署同一包，并做生产验收。

证据至少记录功能文件、测试、验证脚本、上游资源、依赖清单和配置的摘要，以及命令、环境、退出码与执行时间；浏览器检查应记录目标 URL／部署身份。仅提交号不足以识别有未提交改动的输入。

部署前若这些输入变了，应使相关证据失效并按发布门槛重新验证；同一轮已通过且完整输入未变时不重复执行或读取完整日志。首次完整发布验证不能被历史报告替代。线上验收必须另外执行。

这减少无意义的重跑与模型调用，既有完整发布要求不变；缺乏可信摘要或有新增失败时不能使用复用机制。

### 4. 浏览器与资源批量执行，模型按异常读取

保留全部 56 组基础布局检查，用一次矩阵执行返回本地 28/28、生产 28/28及异常列表；改动页面另跑必要的功能专项。语言、视口、展开状态、异步战斗完成、控制台错误和滚动行为需有明确断言，不能只截屏后标记通过。

所有截图、DOM 与控制台证据保留。稳定布局自动断言可批量完成，涉及视觉设计的改动仍需读取相关截图；未知视觉问题不能仅靠“宽度没有溢出”判定正确。

公开资源的路径由本次发布包清单生成，本地和线上分别对照该清单；不要重复列出每个成功文件。单独保留托管 HTML 注入规则与路由代理断言。

### 5. 控制阅读范围与等待输出

默认只读发布流程、状态及必要协作约束，最新报告按需要核对限制；不整份读历史归档、生成代码或原始游戏资源。DESIGN 的旧锚点兼容区无需参与常规发布阅读。

程序批量完成语法、引用和资源检查；完整测试与独立审计分别执行，避免已经完整对照后再运行其战斗子集。长任务使用有界等待，只在新结果／失败时展开输出，不反复返回相同日志。认证检查由部署工具明确结果决定，认证有效时无需每次重新登录。

## 实施顺序、目标与边界

1. 先做日志落盘、摘要输出和阅读范围限制：实现成本最低，无需改变验证门槛。
2. 再将打包、资源清单、文档链接与语法检查固化为通用脚本。
3. 最后固化浏览器矩阵、输入摘要和三阶段编排，保留失败诊断与视觉核验路径。

合理的试运行目标是：同范围且无失败的发布，检查成功输出控制在约 2,000–4,000 token；核心发布阅读与检查摘要合计约 5,000–10,000 token，另计实际必要的页面规则、工具调用、报告和人工判断。这是目标预算，不是已经达成的真实发布总 token。

如果旧流程确实把完整测试明细、重复 DOM 和历史文档返回给模型，可将这部分新增可见文本压缩约 50%–80%作为试验目标；否则收益会更低。不能保证实际模型总用量同比下降，也不能保证优化脚本首次建设时省 token；长期复用才可能摊薄建设成本。

此次没有减少完整测试、独立算例、生成校验、双语窄屏或生产验收，也没有擅自改为“补丁只做冒烟”。如需调整验证覆盖，应作为另一项范围变更单独评估。
