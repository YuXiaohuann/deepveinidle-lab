# userscript 捕获卡顿调研

本报告保留调研阶段证据及方案语境；后续本地实现与本轮专项验证见 [Worker 实施报告](userscript-worker-implementation-2026-10-14.md)。下文“未实现／未修改”指调研阶段。

本次范围为源码核查、授权 Chrome 页面观测及方案研究；未修改功能、安装脚本或部署。优化方案尚未实施，也未验证改善幅度。

## 结论

当前 2.5.2 存在可明确减少的主线程工作：全量消息重复 JSON 解析、完整角色对象深拷贝、同帧多次角色保存、累计市场缓存反复全量复制及无界串行写入队列。它们是优先排查和优化对象，尚不能把真实页面的卡顿或断连确定归因于其中某项。

按用户提出的主线程最小化方向，建议采用专用 Worker 负责解析、裁剪和状态合并，同时保留按帧聚合及有界保存。当前推荐是 Worker 方案；下述局部优化作为其内部设计，不再作为先行主线程实现。

- 页面加载游戏入口为 `index-CU7zVxCz.js`；本次不开展上游计算核验。

## 源码中的开销路径

| 路径 | 已核查事实 | 影响与判断 |
| --- | --- | --- |
| WebSocket message | 同源 `/ws` 的每条字符串消息均立即 JSON.parse | 即使最终没有角色或市场消息，也发生解析；工作位于消息回调内 |
| clonePlayer | 对完整 you 对象 JSON.stringify，逐键正则过滤，再 JSON.parse | 不是仅提取导入字段；字段与历史记录增长会增加遍历、分配及存储输入 |
| frameReceived | welcome、snapshot、windows、guild 各自都可能调用 capture | 同一帧可复制保存多次；仅 windows/guild 更新也再次复制整个角色 |
| serial / marketSerial | 每次更新先制作快照，再追加 Promise 写任务 | 串行保证顺序，不限制积压；写入慢时旧快照仍占内存并等待保存 |
| writeMarket | 每次报价变化复制整个累计 market | 单个报价更新成本随已捕获变体数量增长 |
| marketDepth | every、map、展开 Math.min/max | 可用单次循环减少分配；极大数组还存在展开参数数量限制，但本次未证明真实深度达到该规模 |
| MutationObserver | 长期观察整个 document 子树；提示隐藏后仍检查 ID 并调用 mount | 属次要常驻开销，尚无证据表明它是主要卡顿来源 |

`await GM_setValue` 和 `.then` 不意味着整个捕获流程已经离开主线程；当前重复制发生在入队之前。单纯改成 async 或 Promise 不会消除该成本。

## 推荐实施范围

1. **每帧聚合一次。** 按原顺序处理 welcome 重置、角色、公会及窗口消息，帧末最多生成一次最终角色状态，避免发布中间状态；跨连接标识和旧连接隔离继续保留。
2. **字段白名单。** 先审计战斗、强化、采集、制造及精通消费者，再复制所需字段。当前明确依赖包括 lastTick、skills、equipment、食物配置、brews/brewTier/brewBuckets、house/houseFurniture、masteries、perks、guildBonus、homeBank、ironman、bank、pack、overflow、collections、forgeLog；顶层 guild、worldBuffs、worldTick 保留。不能删除强化物品清单或精通成本所需字段。白名单内嵌套结构也应复制，避免引入不需要的附属内容。
3. **有界合并写入。** 每类最多一个进行中写入和一个最新待写状态，后续更新替换待写状态；市场先完整合并不同 itemId、ask/bid 及各侧原始捕获时间，再合并保存，不能简单丢弃中间市场消息。连接切换必须使旧待写失效，并在旧进行中写入结束后保证新连接清空／新状态最终落盘。
4. **独立任务调度。** 消息回调尽快结束，将复制和写入准备放到后续任务；起始合并窗口可试验 100–250ms，并设最大等待时间，避免持续消息导致一直不保存。调度前记录真实捕获时间，不能用落盘时间冒充行情时间。页面关闭前的最后一段更新可能未落盘，须作为候选方案的明确取舍并验证。
5. **减少常驻观察。** 提示不可见时断开 DOM 观察器；需要显示时重新挂载并观察。成功仍只在保存完成后展示，错误继续明确显示。

维持当前桥接和存储协议是优先目标；是否确实兼容，须由消费者及现有协议测试验证，不能只因版本号未改就宣称兼容。实施前按项目流程先更新技术设计和验收，现有“完整 own-role 捕获”测试应改为全部必要字段保留和无关字段排除。

Chrome 官方说明任务分割需真正让出主线程，可在支持时使用 scheduler.yield，并准备兼容回退；微任务链不能代替渲染机会。参考：[Chrome scheduler.yield](https://developer.chrome.com/blog/use-scheduler-yield?hl=en)。一次巨大 JSON.parse 本身不能靠 yield 分割，所以调度只能改变执行时机，不能降低其总解析成本。

## 推荐 Worker 架构（未实现）

主线程保留同源 `/ws` 构造旁听、连接代次、原始字符串转交、GM 存储及小型提示更新。Worker 负责 JSON.parse、消息类型识别、角色字段白名单、窗口与公会状态、市场深度归并、异常统计及快照生成。游戏自己的消息处理不变，脚本不发送游戏命令或增加连接。

数据流为：WebSocket 原始字符串 → Worker 解析并合并 → 按需输出最新保存快照 → 主线程 GM 保存 → 成功／失败回执。不要在主线程先解析或 stringify，也不要为了 transferable 在主线程把字符串编码成 ArrayBuffer；这会引入新的主线程遍历和分配。字符串通过结构化克隆传递，不能声称零复制或零主线程成本。

### 调度、背压与正确性

- 在 document-start 立即安装 WebSocket 旁听，同时启动单个复用的 Blob Worker。Worker 源码随 userscript 内置，不运行时下载远端脚本；连接建立可以先于 ready，启动队列必须设消息数和字符总量上限。
- 每条转交消息附带连接代次、序号和主线程接收时间。Worker 按接收顺序处理；市场各侧时间使用接收时间，而非 Worker 处理或保存时间。同帧完成后才更新一次角色状态。
- 不能随意丢弃原始消息：windows、公会、市场各 itemId 和 ask/bid 都可能是独立增量。处理积压采用 ACK 统计未完成的消息数及字符量；触及上限时明确报告捕获过载并停止本轮捕获，不能以丢帧后仍显示成功来掩盖缺数据。阈值须由实际流量测量确定，不能当作已验证参数。
- Worker 保留最新角色及累计市场状态，分别维护 dirty/revision。主线程每类最多一个保存中快照；仅当空闲且需要保存时向 Worker 请求最新快照。保存期间 Worker 继续合并，不持续回传快照，避免主线程累积对象或每条消息触发 GM 序列化。
- 可试验首次 ready 后尽快保存、持续更新按 100–250ms 合并；必须有最大等待时间。这个间隔是待测起点，不是性能结论。GM API 仍由 userscript 调用，Worker 中不可直接使用管理器授权 API。
- 新连接立即提升代次，废弃旧输出和待请求；已经进入 GM 的旧写入不能假设可取消。每个存储键的写入必须跨代次串行，新连接清空／新快照排在已开始的旧写入之后。角色保留最近成功快照、市场清空的现有语义须按当前协议核验，不新增旧缓存成功提示。
- Worker 创建异常、ready 超时、error、messageerror、处理异常或过载均明确显示捕获失败；终止 Worker 并释放对象 URL。不自动回退到主线程解析；不静默重启并继续使用缺少初始状态的增量，恢复需要刷新或新的完整初始化。
- 提示仅在对应代次的实际保存成功后显示；隐藏时断开 DOM 观察器，需要新提示时再挂载。页面退出时终止 Worker；不承诺异步最后一次保存一定完成。

### 当前浏览器可行性证据

2026-10-14 在授权 Chrome 游戏页通过 CDP 临时创建 Blob Worker，仅传递合成字符串；Worker 返回长度 14，消息往返成功。随后已 terminate、清除超时并 revokeObjectURL，没有留下 Worker 或修改游戏逻辑。这证明当前页面上下文允许该测试，不代表 userscript 沙箱、其他脚本管理器或以后 CSP 均可用，实际安装环境仍需验证。

Worker 构造受页面策略及运行上下文影响，Blob 路径不能保证跨环境可用；原始字符串和输出对象通过 postMessage 的结构化克隆产生传递成本。参考：[Worker 构造及 CSP](https://developer.mozilla.org/en-US/docs/Web/API/Worker/Worker)、[结构化克隆](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Structured_clone_algorithm)、[脚本管理器授权 API](https://www.tampermonkey.net/documentation.php?locale=en)。

### 实施影响

仅调整角色 userscript 捕获执行位置与调度，保持实验室消费者、角色桥接 2.4、数据协议 2、市场桥接 1.0 及现有存储键兼容。实施前先更新技术设计及验收；Worker 主体宜用可独立测试的函数内置进单个安装脚本，避免额外构建／远端依赖。相关测试需同时覆盖纯 Worker 状态处理、主线程存储协调以及实际浏览器／脚本管理器集成；仅模拟 Worker API 的测试不足以证明可安装。

不建议通过修改游戏 JSON.parse、预测 getter 或主动请求新快照解决；这会扩大与游戏实现的耦合，且不直接解决复制和积压。

## 后续验收

- 先在同一浏览器、同一页面状态比较启用／停用脚本，再比较原版／候选版；分别覆盖刷新首次捕获、持续战斗、市场分类及深度切换。
- 增加仅输出汇总的临时性能计数：消息长度、解析时间、裁剪时间、GM 调用与完成时间、保存字节规模、待写数量及丢弃旧待写数量；不记录消息正文。
- 记录长任务、帧间隔、交互延迟、内存及断连时间；区分加载游戏本身和脚本增量，不凭一次长任务判断掉线原因。
- 回归全部配置导入，尤其强化物品清单与精通 collections/forgeLog；覆盖同帧多消息、慢存储、报价两侧独立时间、空报价、失败提示和跨连接隔离。
- 性能目标建议为脚本自身处理不产生超过 50ms 的单任务，待写数量有固定上限，最终缓存为最新合法状态；这是验收建议，尚未达到或验证。
