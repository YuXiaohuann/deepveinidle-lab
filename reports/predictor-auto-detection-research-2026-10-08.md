# 预测入口自动识别调研

## 结论

可以消除捕获逻辑对固定压缩函数名的依赖，自动适配单纯改名；不能据此承诺自动兼容任意游戏更新。本次为调研，未修改产品行为。

推荐保留当前 JSON 解析观察与 bankOrder getter，在游戏资源上增加只读 AST 定位，再根据调用栈的资源 URL、行列位置识别预测调用。解析源码，不执行源码，不替换游戏模块，不主动预测。自动捕获和计算兼容分开处理。

上述候选筛选是可行性试验，不是最终可直接上线的识别器。实施时必须检查字段所属节点、参数与数据流、角色克隆调用关系及返回对象，不能只按字符串出现判断。

## 建议实现

1. 从实际加载的游戏脚本识别资源 URL，读取该公开同源资源并计算摘要，避免硬编码 index 文件名；记录实际加载与所读资源一致性，异步读取期间先不认定预测捕获。
2. 使用本地打包的解析器识别唯一预测入口及角色克隆读取点。候选为零、多个或关系不匹配时明确报错；不宽松猜测，不接受任意 bankOrder 读取。
3. getter 仍捕获实际页面角色对象。在 Error.stack 中解析脚本 URL、行列位置，映射到源码范围，并核对克隆与预测之间的调用关系；不检查固定函数名。源码位置每个构建自动重算。
4. 保留完整角色、seed/windows、连接隔离、独立克隆、串行存储。资源解析完成前已发生的预测不冒充已捕获数据，应提示重新触发预测；不能为了补数据主动调用游戏预测。
5. 快照记录资源摘要和识别结果。捕获成功与模拟器支持状态分别展示；未知计算版本仍拒绝模拟，不再统一误报“尚未捕获”。

最简过渡方案是 AST 自动提取当次函数名后沿用栈名字比较；能解决固定名单维护，但仍依赖运行时名字展示。按源码位置识别更符合“不依赖预测函数名”的目标。

## 其他方案

| 方案 | 判断 |
| --- | --- |
| 任意 bankOrder 读取都捕获 | 不采用：普通克隆、状态导出与序列化也会读取，无法证明预测发生 |
| 靠打开预测界面、点击或延时捕获 | 不采用：界面有异步计算与缓存，不能保证对应实际读取时点 |
| Function.caller 或搜索 window 全局函数 | 不采用：当前入口在 ES module 内部，不能依赖全局暴露或调用者访问 |
| 替换脚本并注入入口包装 | 不优先：改变游戏执行路径，维护和浏览器兼容成本高 |
| AST 定位加源码位置调用栈核对 | 推荐原型验证：不依赖函数名，不改写游戏执行代码，但仍依赖结构与栈信息 |

## 兼容边界与验收建议

- Error.stack 非标准，V8、Firefox、Safari 格式不同，需各自解析并真实浏览器验证。来源：[MDN Error.stack](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Error/stack)。不支持的格式明确失败。
- getter 可位于 userscript 所在 realm，运行时栈深度、异步调用和内联均需实测；不能把 Node 可行性当浏览器通过。
- 入口被内联、角色克隆策略改变、字段改名、脚本拆分或 Web Worker 化，超出“仅函数名变化”范围，应停止并提示需更新识别规则。
- 不仅测试改名成功，还要验证普通克隆与序列化不捕获、多候选拒绝、资源读取失败、首次计算早于定位完成、旧连接隔离以及真实预测逐数对照。
- 自动允许新构建模拟，需要比较整个计算依赖闭包的语义指纹，包括作用域绑定、属性、字面量、依赖关系与数据表。简单删除所有标识符或仅比较预测入口会掩盖规则变化。此项比入口识别大得多，建议后续单独设计。
