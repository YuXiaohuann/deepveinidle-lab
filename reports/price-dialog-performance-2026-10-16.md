# 物品价格弹窗卡顿调查

日期：2026-10-16。调查基线：`b0e0acb`。本次仅测量与诊断，没有修改应用代码、计算或交互，没有提交或部署。

## 结论

已在本地复现。主要原因是默认同步渲染完整物品表，产生上万 DOM 元素；重复打开时先将保留的整棵 DOM 显示为模态，再无条件重建弹窗并恢复滚动，引发两段高成本样式／布局工作。候选 ID 计算、事件绑定和行情读取不是本次测量的主要耗时项；所有开窗场景行情 API 请求数均为 0。

即使没有市场缓存，默认仍生成 1,265 行（所有合法品质的未强化物品），并非只显示报价项。使用已保存的官方行情样本后，强化／品质变体将表格扩大到 1,543 行。`.price-list` 的高度上限和滚动容器只限制可视区域，没有减少实际生成或参与布局的行数。

## 未修改代码的测量

环境：本机 macOS、无头 Chrome 155；1280×900 桌面及 390×900 窄屏，独立浏览器上下文，没有真实账号或用户会话。官方行情样本来自此前保存的公开 JSON，使用正常价格适配／导入函数构造含 1,044 条报价、387 条有效价的本地状态。每种情形记录连续四次打开；首次与后续重开分开看，以下均为本次实测范围，不是生产统计或用户设备保证。

| 场景 | 物品行／弹窗内元素数 | 首次同步处理 | 后三次同步处理 |
| --- | --- | --- | --- |
| 空价格与行情，桌面 | 1,265／16,743 | 88.9ms | 150.2–193.9ms |
| 官方行情样本，桌面 | 1,543／20,357 | 130.3ms | 196.4–230.6ms |
| 同样数据，矿石筛选已生效 | 40／818 | 已预先打开以设置筛选 | 四次均为 12.2–12.5ms |
| 官方行情样本，390px 窄屏 | 1,543／20,357 | 134.1ms | 191.2–228.2ms |
| 官方行情样本，浏览器 CPU 4 倍降速 | 1,543／20,357 | 540.8ms | 890.2–945.1ms |

“同步处理”为原生点击处理函数的主线程耗时。另记录点击开始至后续两个动画帧的间隔，用于观察后续布局与呈现安排，不能等同真实用户输入到屏幕显示的精确延迟。桌面官方行情样本的该间隔为首次 166.6ms、重开 238.6–285.2ms；CPU 降速为浏览器模拟，不代表真实低配设备的测量。

## 分段与源码位置

使用仅通过浏览器路由替换的内存插桩做分段，对照原始模块的结果接近。插桩有开销，数字用于归因而非替代上表基线。

1. `src/item-price-controls.js:109`：开窗固定调用 `showModal(); render();`。初次弹窗空，`showModal()` 约 0.9ms；关闭后 DOM 保留，重开 `showModal()` 约 74.7–87.4ms。
2. `src/item-price-controls.js:59` 与 `:70`：对整个弹窗赋 `innerHTML`，并对完整结果执行 `rows.map(row)`；既重建分类与过滤控件，也重建千余行价格输入框和复选框。样本中重开 HTML 设置约 21.6–27.7ms，随后重新绑定事件约 1.5–7.9ms。
3. `src/item-price-controls.js:90`：重建后立即设置 `.price-list.scrollTop`。原生滚动位置写入在这里同步承担了待完成的样式／布局工作，实测约 75.1–84.0ms；它不是单纯修改一个数值的成本。CDP 同样观测到重开整段的布局约 86.7–102.0ms、样式重算约 62.7–66.4ms。
4. `src/item-price-controls.js:38`：候选物品生成约 1.3–3.6ms；逐行 HTML 内容生成约 15–17ms（含报价数值本地化），均显著小于浏览器处理完整表格的成本。API 次数为 0，不存在等待官方行情导致的开窗阻塞。

CPU 样本亦主要落在 `render` 和原生 `showModal` 的调用范围。JS 函数归属内可能包含原生 DOM／布局耗时，不能把这些样本全部解释为 JS 算法计算。

| 对照 | 同步处理 | 点击至后续两帧 | 含义 |

## 建议与边界

优先采用简单分页（例如每页 100 条），减少同时存在的表格控件；完整筛选结果、物品价格、手动编辑及“全选当前筛选结果”的数据范围仍应保留，不能直接截掉剩余条目。其次在语言、价格、筛选没有变化时复用弹窗 DOM，避免每次打开无条件重建。后续可再合并局部状态更新及调整布局读写顺序；仅缓存候选列表、移动到下一帧或移除滚动恢复不足以解决主要瓶颈。

分页会改变列表交互，须先更新设计与验收，再实施；本次没有实施优化。没有运行功能单元测试或完整发布检查。本次测量证明当前本地提交存在可复现的渲染瓶颈，不代表已检查用户当前浏览器、真实存档、扩展或生产环境的全部影响。

原始记录保存在 `.test-artifacts/price-dialog-profile/`：`profile.json`、`profile.log`、`official-reopen.cpuprofile`、`experiments.json` 和 `experiments.log`；`run.mjs` 与 `experiments.mjs` 为本地诊断脚本。所有场景均完成且无页面脚本错误。

## 无筛选时不显示物品的方案评估

按后续提出的方案，在隔离浏览器内增加默认筛选状态的提前返回，未修改应用文件。沿用同一份官方行情本地样本、桌面视口和四次测量；物品数量仅统计实际价格输入行，不包含空状态占位行。结果保存于同目录 `filter-gate.json`、`filter-gate.log` 与诊断脚本 `filter-gate.mjs`。所有场景无页面脚本错误，API 请求均为 0。

| 筛选条件 | 物品数 | 同步打开处理耗时 |
| --- | --- | --- |
| 无筛选，不生成物品行 | 0（弹窗内仅 300 个元素） | 首次 16.1ms，重开 6.0–6.7ms |
| 仅“未定价” | 1,156 | 150.7–190.2ms |
| 仅“未锁定” | 1,543 | 211.0–217.9ms |
| 仅“普通”稀有度 | 298 | 39.8–43.8ms |
| 仅“武器”分类 | 260 | 37.5–51.0ms |

结论：方案可明显改善默认开窗，实施范围小，适合作为独立的第一步优化。设置宽泛筛选后仍可能生成完整或接近完整的表格，所以它不能保证所有筛选／重开场景流畅；保留上次筛选时，重开仍显示该筛选结果并承担其渲染成本。

若实施，建议将“无筛选”严格定义为分类=全部、去空白后的搜索为空、稀有度=全部、强化=0（当前含义为全部）、状态=全部同时成立。五项中任何一项为具体条件即可显示匹配物品；普通稀有度的值虽然是 0，仍是有效筛选。上方分类价格来源选项是导入偏好，不算物品列表筛选。

无筛选时显示双语“请先设置筛选条件”，与“没有匹配物品”区分；不显示已报价或已设置物品，全选／批量锁定操作禁用并清除旧勾选。导入、清空未锁定价格仍按原来的全局范围工作，不能因为空列表而跳过价格应用；导入成功但未设置筛选时仍保持列表为空。数据及有效价格不删除。上述仅为建议规则，尚未写入当前产品设计或实现。
