# 角色捕获 Worker：实际 Chrome 验证

## 结论

2026-10-14 用户自行更新脚本后，在授权的 Chrome 游戏页确认实际加载 2.6.0，并验证实际脚本管理器中的角色及市场存储、实验室只读桥接正常。原始消息主线程转交耗时较小；目前没有同负载旧版对照，不能量化提升比例，也不能宣称整体卡顿或断连已消失。

本轮没有修改功能、安装脚本或部署；仅增加验证证据及更新状态。临时计时探针已移除，Worker 的 postMessage 已恢复原生方法，调试器和性能观察器均已关闭。

## 环境与方法

- Chrome 已登录真实游戏页，读取已加载 userscript 源码元数据确认版本 2.6.0；从安装脚本的执行作用域临时包装其 Worker.postMessage，计量原始字符串转交和 ACK 往返，不保存消息正文或角色具体配置值。
- 通过现有角色／市场 CustomEvent 只读桥接访问实际 GM 缓存，只返回保存时间、字段名及条目计数；未点击导入，不改变实验室配置或有效价格。
- 刷新一次游戏验证首次角色捕获，随后浏览市场全部、矿石、金属锭、鱼及木材分类；没有交易、游戏任务调整或主动接口请求。
- 页面 PerformanceObserver 与 requestAnimationFrame 分别观测持续战斗、打开及浏览市场、稳定市场。页面长任务包含游戏、其他扩展和诊断开销，不能直接归因于角色脚本。

## 失败路径与证据边界

- 当前 CDP 不开放 Target.getTargets、Target.setAutoAttach 或 Page.addScriptToEvaluateOnNewDocument，未取得 Worker 目标列表或从导航开始的完整性能记录；本轮未获取 CPU 调用栈。
- 最初尝试通过 Runtime.executionContextId 读取脚本沙箱中的探针没有有效返回，其中一次超时；之后改由不暂停的源码诊断点输出汇总。该前段 ACK 最大值达 7.1 秒，受诊断干扰，明确排除出正常性能结论。独立窗口重新包装后才记录上述 ACK 指标。
- 初次尝试重置旧探针未实际形成新窗口，因此未把该段累计 ACK 当作独立结果；后续独立窗口用不同 Worker 属性记录，最终一起恢复原生 postMessage。
- DOM role 定位市场分类未匹配，随后使用刷新后的无障碍控件标识完成操作；未将未执行的点击记为成功。
- 页面长任务和捕获时序没有同负载旧版／停用脚本对照；GM 序列化和实际写入耗时没有单独量出。暂不提出“提升 N%”“卡顿已解决”或“断连由脚本导致”的结论。
- 本轮只验证当前用户的 Chrome 与脚本管理器组合；后台标签节流、其他管理器、其他浏览器、极端行情及长时运行仍未覆盖。

## 后续判断

Worker 化已经在真实安装环境运行，且消息转交本身没有出现接近 50ms 的耗时；剩余市场打开长任务值得另行获得 CPU 栈后归因。若用户仍感到卡顿，下一步应对市场打开时的游戏列表渲染、GM 存储及其他扩展分别作配对测量，而不是继续增加未经测量的捕获逻辑。
